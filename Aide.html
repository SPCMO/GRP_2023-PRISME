Utilisation

À quoi sert cet outil

PRISME : Paramétrage, Recherche Itérative et Sélection du Meilleur Étalonnage.

GRP_2023-PRISME remplace la « boucle magique » (boucle_magique_relatif_absolu_HOR1_pdf.py) : un collègue avait écrit un script qui boucle sur des horizons de calage et rejoue des crues historiques pour trouver le meilleur horizon/seuil de calage du modèle hydrologique continu GRP (INRAE). Ce script contenait un bug critique (voir Correctifs) et n'était utilisable qu'en éditant le code Python à la main. Cet outil offre la même logique via une interface graphique, fiabilisée, et réutilisable pour n'importe quel bassin (pas seulement Moussoulens).

Premier lancement

Double-cliquer sur Test_pr_install.bat (vérifie/installe l'environnement Python), puis sur Lancer_GRP_2023-PRISME.bat.

Onglet Configuration

Dossiers de travail : 4 boutons Parcourir pour désigner 00_GRP_v2023, 00_Donnees_<station>, 00_BDDTR_<station> et 00_Resultats_<station> — leurs sous-arborescences sont fixes (imposées par les exécutables GRP), l'outil les déduit automatiquement une fois ces 4 chemins renseignés.

Identification station (PHyC) : saisir le code station (10 caractères : 1 lettre + 9 chiffres, ex. Y161202001) puis cliquer sur « Identifier via PHyC ». L'outil en déduit automatiquement le code site (8 caractères, les 2 derniers chiffres retirés — ex. Y1612020), qui est le code réellement utilisé dans LISTE_BASSINS.DAT et dans les noms de fichiers/dossiers générés par GRP. Le nom de la station, son code BNBV, sa surface de bassin versant (km²) et ses 6 seuils de vigilance en débit (ZT jaune/Jaune/ZT orange/Orange/ZT rouge/Rouge) sont récupérés et affichés — la surface est parfois approximative (repli sur la surface de la BNBV quand PHyC n'a pas la surface précise du site), signalé explicitement dans ce cas. C'est aussi ce bouton (et lui seul — taper dans le champ ne suffit pas) qui détermine la base de résultats utilisée : si le code station saisi diffère du précédent, un message précise si une base vierge sera créée pour cette nouvelle station ou si une base existante est reprise (avec son nombre de combinaisons déjà enregistrées) — voir Architecture > "Réutiliser pour un autre bassin".

⚠️ Ces seuils PHyC sont différents des champs SeuilV1/SeuilV2/SeuilV3 internes à LISTE_BASSINS.DAT (utilisés par GRP pour sa propre analyse des résultats) — ne pas les confondre. Les deux sont affichés séparément dans le Dashboard.

Les identifiants PHyC (idcontact/mot de passe) sont demandés à la première identification et enregistrés dans config/config.json (jamais versionné dans le dépôt git).

Dossier de stockage des bases de résultats (optionnel) : par défaut, les bases (data/runs_<code_station>.sqlite3) vivent dans le dossier d'installation de l'outil — invisibles pour toute réinstallation future dans un autre dossier (mise à jour faite en clonant/copiant à côté plutôt qu'en place), qui repartirait alors avec une base vierge sans que l'ancienne ne soit signalée. Bouton Choisir un dossier externe… pour déplacer ce stockage vers un dossier stable, hors de l'installation de l'outil : réglé une seule fois sur un poste, il est retrouvé automatiquement par toute future réinstallation de l'outil sur ce même poste, même dans un tout nouveau dossier (voir Architecture > "Éviter de perdre ses résultats lors d'une réinstallation"). Propose de copier les bases déjà présentes vers le nouveau dossier choisi (jamais automatique/silencieux). Bouton Revenir au dossier par défaut pour annuler ce réglage.

Onglet Paramétrage

Choisir un pas de temps de calage, puis cocher les horizons à tester parmi ceux définis pour ce pas de temps (boutons « Tout sélectionner »/« Tout désélectionner »). Le bouton Paramètres… ouvre un écran dédié pour ajouter/modifier/supprimer/réorganiser aussi bien la liste des pas de temps que, pour chacun, la liste de ses horizons possibles — rien n'est codé en dur dans le programme.

Définir ensuite les seuils de calage (SeuilC1, en m³/s — débit minimal au-dessus duquel le calage est effectué, pour éviter de perturber le modèle en basses eaux) via une liste éditable, et cocher la ou les méthodes de correction à tester (Tangara / RNA — les deux cochées lancent les runs successivement pour chaque méthode, GRP n'acceptant qu'une seule méthode à la fois en mode BDTR).

Instants de rejeu supplémentaires (avant le pic) : liste éditable, vide par défaut, d'heures avant le pic RÉEL de chaque crue (ex. 24, 12, 6) à rejouer EN PLUS du rejeu habituel (positionné par GRP à la date de début de la crue, ~2j avant le pic selon le champ NJ de LISTE_BASSINS.DAT). Sans reprendre le calage — même dossier BDTR déjà calibré — pour comparer le comportement du modèle selon qu'il démarre bien en amont ou en pleine montée de crue. Voir Architecture > "Rejeu à plusieurs instants avant le pic" pour le détail technique et le coût en temps.

Les listes seuils de calage et instants de rejeu (comme les listes de l'écran Paramètres…) acceptent la sélection multiple (Ctrl/Maj + clic) : le bouton Supprimer retire alors tous les éléments sélectionnés en une fois (confirmation demandée au-delà d'un seul), et un ascenseur vertical apparaît dès que la liste dépasse la hauteur visible.

Conseil : une campagne complète (tous les horizons × tous les seuils × toutes les crues) peut être très longue. Lancez d'abord une campagne sur quelques horizons/seuils espacés (grille grossière), consultez le Dashboard pour repérer la zone prometteuse, puis affinez avec une seconde campagne resserrée — les résultats des deux campagnes se cumulent automatiquement, pas besoin de tout refaire.

Onglet Crues

Les crues ne sont plus une liste figée dans le code : elles sont détectées automatiquement par GRP lui-même, lues depuis CRITERES_PERF.DAT (généré par le calage complet, exe 01 + exe 03) — chaque vignette affiche la date, le débit de pointe (avec l'horodatage du pic) et le cumul de pluie de l'épisode. Les indicateurs dQP/dTP/VE/KGE de CRITERES_PERF.DAT (calage actuellement en place, sans rapport avec une combinaison de campagne PRISME) ne sont volontairement pas affichés ici — retirés à la demande explicite de l'utilisateur, qui n'y voyait pas de sens dans cet onglet. Une case « Inclure aussi les événements de pluie » élargit la liste aux événements pluviométriques (par défaut, seuls les événements de débit sont affichés). Cocher les crues à inclure dans la campagne. Les vignettes sont groupées par niveau de vigilance max atteint, du plus sévère (Rouge) au moins sévère (Vert), triées par n° d'événement croissant au sein d'un même niveau.

Onglet Analyse crues affl.

Analyse la contribution des stations affluentes à l'hydrogramme observé à la station exutoire (Moussoulens), indépendamment de tout calage GRP (aucune campagne requise). Bandeau Dossier d'import des débits affluents : dossier par défaut du sélecteur de fichier ci-dessous. Bandeau Stations affluentes et temps de propagation à la station exutoire : gestion (Ajouter/Modifier/Supprimer) de chaque affluent — code station et bouton « Récupérer infos PHyC » (pré-charge le nom et la surface de BV depuis PHyC, tous deux modifiables ensuite), nom, surface de BV (km²), temps de propagation jusqu'à l'exutoire en P10/P50/P90 (format hh:mm, P50 obligatoire, P10/P90 facultatifs), fichier de débits (CSV date;res, même format de date AAAAMMJJHHMM que les EVxxxx.DAT — voir modules/affluents.py) et couleur de la courbe. Cette configuration (dossier d'import + liste des affluents) est désormais persistée par station exutoire dans config/config.json (clé affluents_par_station, indexée par code_station) : rebasculer l'outil sur une station déjà étudiée restaure automatiquement ses affluents, sans avoir à les ressaisir.

Pour la crue sélectionnée (pas de temps + crue, flèches ◀▶ comme Détail par crue) : Qobs de l'exutoire en trait plein bleu, débits affluents en pointillés, hyétogramme de la pluie de bassin de l'exutoire, seuils de vigilance PHyC (case à cocher pour les masquer — un seuil au-delà de l'échelle Y actuellement affichée est ignoré, plus de flottement hors cadre), survol à la souris pour lire une valeur exacte (comme OPALE v2). Couleur d'une courbe affluente modifiable en cliquant sur son entrée dans la légende. Bandes verticales de propagation semi-transparentes (P10-P90, couleur de l'affluent, trait épais à P50), calculées à partir du pic de cet affluent propagé sur l'axe de l'exutoire. Barycentre temporel de la pluie de bassin (calculé uniquement sur les pluies tombées avant l'horodatage du Qmax exutoire — icône ⓘ à côté de l'étiquette pour le détail) marqué d'un point bleu foncé sur le bord haut du graphique, avec son horodatage en étiquette. Temps de réponse (Tr = horodatage du Qmax exutoire − barycentre) affiché à la fois juste après cet horodatage ("-> Tr = XXh XXmin") et dans le titre de la légende, avec en dessous les P10/P50/P90 du Tr calculés sur l'ensemble des crues actuellement sélectionnées pour la campagne (P50 en gras, taille normale ; P10/P90 en plus petit). Camembert de contribution au pic exutoire sous la légende, à partir des % de Q rétropropagé de chaque affluent (débit de l'affluent à l'instant [Qmax exutoire − son P50] — pas son propre Qmax) : écrêté au prorata si le total dépasse 100 %, complété par une part grise « Écoulements locaux » s'il est inférieur à 100 % — total (somme des % des affluents) affiché sur une 2e ligne sous le titre du camembert, en gras rouge si supérieur à 100 % (signal d'alerte visuel).

Vignettes Qmax + horodatage de chaque courbe, à droite du graphique sous la légende — surface de BV affichée sur chacune quand elle est connue (y compris celle de l'exutoire, identifiée en Configuration). En dessous, un camembert « Surface de BV suivie » (couleurs éclaircies "semi-transparentes", % de chaque part affiché au-delà de 5 %, total en titre) montre le prorata de surface des affluents actuellement tracés par rapport à la surface totale du BV exutoire — écrêté au prorata si le total dépasse 100 %, part grise « Écoulements locaux » pour le reste non couvert par un affluent suivi (même principe que le camembert de contribution au pic de débit, mais en surface). Tableau Volumes transités et Q - exutoire et affluents : volume transité (intégration trapézoïdale, hm³) et Q rétropropagé au pic exutoire pour chaque station, avec le % de chacune par rapport à l'exutoire (icône ⓘ cliquable sur l'en-tête de colonne pour le détail du calcul). La liste des stations affluentes et le tableau des volumes ont chacun un fond éclairci (« semi-transparent ») assorti à la couleur de leur courbe, pour identifier une ligne d'un coup d'œil.

La case « Afficher les seuils de vigilance » a aussi été ajoutée à Dashboard > Détail par crue pour cohérence. Le pas de temps sélectionné est partagé et synchronisé EN DIRECT entre les 5 onglets qui en proposent un (Paramétrage, Campagne, Dashboard > Détail par crue, Crues, Analyse crues affl.) — le changer une fois n'importe où le change partout. Exportable en Excel depuis Dashboard > Vue synthèse (bouton "Exporter en Excel…", feuille "Analyse crues affl.") : une vignette graphique par crue détectée (tous les affluents configurés, seuils/bandes de propagation/camemberts toujours affichés — pas de cases à cocher dans un export statique) précédée de son tableau de volumes/contributions.

Onglet Campagne

Bouton Nouvelle campagne (tout relancer) : boucle sur toutes les combinaisons horizon × seuil × méthode sélectionnées, et pour chacune, rejoue chaque crue cochée (mode opérationnel temps différé, comme la boucle magique d'origine mais avec le bug du .bat corrigé). La campagne tourne en arrière-plan, la fenêtre reste utilisable. La progression, un tableau des combinaisons avec leur statut, et un journal détaillé s'affichent en temps réel. Ce bouton relance tout, y compris les combinaisons déjà réussies — une confirmation est demandée s'il y en a dans la sélection actuelle (audit ergonomie, voir Correctifs du jour), pour éviter de gaspiller par erreur un calage déjà acquis. Pour ne relancer que ce qui manque, utiliser plutôt le bouton ci-dessous.

Si des combinaisons ou des crues ont échoué (erreur explicite dans le journal), le bouton Compléter la campagne et relancer les échecs ne refait que le nécessaire : si le calage d'une combinaison a déjà réussi ET que LISTE_BASSINS.DAT charge encore physiquement cette combinaison précise, il n'est pas relancé — seules les crues manquantes ou en échec le sont. Cette deuxième condition (ajoutée suite à un bug réel, voir Correctifs du 26/08/2026) force en pratique un recalage à chaque fois que la combinaison en cours diffère de la dernière réellement calée dans le dossier BDTR, partagé entre toutes les combinaisons d'une même campagne — plus lent qu'avant sur une reprise avec plusieurs combinaisons déjà réussies, mais indispensable pour ne jamais rejouer une combinaison avec les paramètres d'une autre. Ce même bouton sert aussi à compléter une campagne déjà entièrement réussie avec des instants de rejeu supplémentaires (voir Paramétrage) ajoutés après coup : une crue dont la référence a déjà réussi mais à qui il manque un instant configuré est reprise pour ce seul ajout, sans repasser par le calage ni refaire le rejeu de référence.

Les instants de rejeu supplémentaires sont journalisés séparément dans le journal ("[instant H-24] ...") mais volontairement exclus de la barre de progression et des colonnes crues_ok/crues_ko du tableau — ces compteurs continuent de refléter uniquement la campagne principale (instant de référence), comme avant l'ajout de cette fonctionnalité. Le bouton "⏱ Estimer le temps restant" affiche, en plus de l'estimation habituelle, un majorant du surcoût de ces instants supplémentaires (nb instants × nb combinaisons × nb crues × durée médiane d'un rejeu — sans déduire ce qui est déjà en base, donc une estimation large, pas précise).

Onglet Dashboard

Bandeau partagé en haut : choix de la pondération du score composite (poids égaux / profil métier / personnalisé, avec asymétrie dTP retard/avance réglable) et sélecteur « Crues dans le score » — restreint, si besoin, le calcul du score à un sous-ensemble de crues choisi à la main (fenêtre listant TypEvt, Vigilance max, Qmax, cumul de pluie de chaque crue). Ces deux réglages s'appliquent à toutes les vues à score ci-dessous, sauf « Variation selon le nb de crues » qui varie N automatiquement et reste volontairement indépendante de la sélection de crues. Chaque sous-onglet se recharge automatiquement dès qu'on clique dessus (nouveaux horizons/méthodes disponibles après une campagne, notamment) — plus besoin de fermer/rouvrir l'outil. Le contenu de chaque sous-onglet devient défilant verticalement si la fenêtre est trop petite pour tout afficher d'un coup (ex. "Détail par crue" sur un écran de petite taille).

Vue synthèse : heatmap horizon × seuil (score composite, 0 = meilleur), classement des meilleures combinaisons, dispersion de |dQP| par horizon. Deux cases à cocher Tangara/RNA au-dessus du graphique permettent de restreindre l'affichage à une seule méthode ou de garder les deux (défaut) — les échelles des axes (horizons, seuils, |dQP| max) restent toujours calculées sur les 2 méthodes confondues, pour rester identiques quel que soit le filtre et permettre une comparaison visuelle directe entre Tangara et RNA. Bouton d'export Excel : une fenêtre de vérification s'affiche avant de choisir le fichier de destination — pondération, station, crues incluses, et les seuils/méthodes RÉELLEMENT présents dans les résultats en base (pas la sélection actuelle de l'onglet Paramétrage, qui ne prépare qu'une prochaine campagne et peut différer, ni les cases "Méthode(s) affichée(s)" ci-dessus, qui ne filtrent que l'affichage à l'écran — l'export contient toujours l'intégralité des résultats). Classeur à 7 feuilles : Paramétrage, Vue synthèse, Détail par crue, Sensibilité au seuil, Vue 3D, Variation selon le nb de crues, Analyse crues affl. — un onglet Excel par sous-onglet du Dashboard et l'onglet Analyse crues affl., plus le contexte de campagne. Le bouton affiche « Export en cours… » (grisé) pendant la génération du classeur, qui peut prendre plusieurs secondes (7 feuilles, figures matplotlib re-rendues) — évite l'impression d'une interface figée qui incitait à recliquer.

Détail par crue : courbe du débit observé (large fenêtre, depuis CRITERES_PERF.DAT) avec une ou plusieurs courbes simulées superposées (liste "Combinaison(s)" à sélection multiple — Ctrl/Maj + clic — avec ascenseur vertical, une couleur/légende par combinaison), les 6 seuils de vigilance PHyC (jaune/orange/rouge + zones de transition — case à cocher pour les masquer), et un tableau du maximum + horodatage de chaque courbe tracée. Flèches ◀▶ à côté du menu "Crue" pour naviguer épisode par épisode (retrace automatiquement avec la même sélection de combinaisons). Survol à la souris pour lire une valeur exacte sur une courbe. Si aucune courbe simulée n'apparaît pour une combinaison, c'est qu'elle n'a pas encore été rejouée pour cette crue précise. La ligne "Crue #N (...) — configuration en place" au-dessus du graphique a son icône ⓘ : ce sont les indicateurs du calage complet actuellement installé dans GRP (CRITERES_PERF.DAT), pas ceux d'une des combinaisons sélectionnées. Sous le tableau des maximums, si des instants de rejeu supplémentaires sont configurés (Paramétrage), une grille "Comparaison des instants de rejeu" affiche un panneau par instant (référence + décalages) pour la crue et les combinaisons sélectionnées ci-dessus — voir Architecture > "Rejeu à plusieurs instants avant le pic".

Sensibilité au seuil : évolution du score composite en fonction du seuil de calage, pour un ou plusieurs horizons superposés (sélection multiple, une couleur par horizon) à méthode fixée.

Vue 3D : nuage de points horizon × seuil × score composite — couleur du point = score (vert = meilleur), forme du marqueur = méthode (rond T, triangle R), meilleure combinaison mise en évidence par une étoile dorée avec le détail de ses indicateurs. Vue orientable à la souris (clic-glisser) ; bouton Réinitialiser la vue 3D sous la légende pour revenir à l'angle initial en un clic.

Variation selon le nb de crues : trace comment la combinaison optimale (KGE médian brut, comparable d'un N à l'autre — pas le score composite, normalisé par N donc non comparable) évolue selon le nombre de crues les plus fortes retenues (Qmax décroissant), avec une 2e ordonnée (violette) montrant l'horizon de la combinaison gagnante à chaque N. Points de bascule repérés par une ligne pointillée ; étiquettes forcées sur chaque point ; sélectionner une ligne du tableau entoure le point correspondant sur les 2 courbes.

Score composite (Dashboard)

Calculé uniquement sur les combinaisons actuellement affichées (jamais sur une seule, ni sur toute la base) :

  1. Pour chaque combinaison, erreur médiane (sur ses crues réussies, pas la moyenne — une crue atypique ne doit pas fausser le score) de 4 indicateurs : |dQP| (%), |dTP| (pas de temps), |VE| (%), et (1 − KGE).
  2. Chaque indicateur normalisé entre 0 (meilleure valeur observée parmi toutes les combinaisons affichées) et 1 (la pire) — échelle relative à ce qui est affiché, pas absolue.
  3. Score final = moyenne pondérée des 4 indicateurs (déjà médians) normalisés, à poids égaux par défaut (25 % chacun) — cette 2e étape reste une moyenne, pas une médiane : les poids n'auraient aucun effet sur une médiane de 4 valeurs.
  4. dTP traité symétriquement : une avance compte comme un retard de même ampleur.

Ce même texte est accessible dans l'outil via le bouton ⓘ à côté de chaque "Score composite" (voir modules/score.EXPLICATION_SCORE). Le calcul lui-même n'a volontairement pas été modifié pour privilégier dQP ou l'avance sur le retard (demande métier des modélisateurs) — voir plutôt l'analyse comparative dans le changelog ci-dessous, qui chiffre l'écart sans toucher au score utilisé par l'outil.

Le score composite n'est jamais stocké en base — aucune colonne "score" dans le schéma SQL (modules/results_store.py) — il est recalculé à la volée, à chaque affichage, à partir des dQP/dTP/VE/KGE bruts déjà enregistrés (Dashboard > Vue synthèse/Sensibilité au seuil/Vue 3D/Variation selon le nb de crues, et Campagne > "Combinaisons déjà réalisées"). Conséquence directe : un changement dans la formule de calcul (ex. moyenne → médiane, voir changelog du 1er septembre 2026) s'applique immédiatement à tous les résultats déjà en base, anciens comme récents, dès le prochain affichage — sans script de migration ni ré-exécution d'aucune campagne.

Une application desktop simple (pas de front/back séparés)

Certains outils métier fonctionnent en application web : deux programmes séparés (un serveur et un navigateur) qui se parlent par le réseau, avec un serveur à démarrer et un port à ouvrir. GRP_2023-PRISME fait le choix inverse, plus simple à installer et à faire tourner sur un poste isolé :

  • Un seul programme : main.py (fenêtre Tkinter)
  • Pas de serveur, pas de navigateur, pas de port réseau à ouvrir
  • L'interface et la logique métier s'appellent directement en mémoire, dans le même processus
  • Un seul poste à la fois — pas d'usage partagé simultané depuis plusieurs postes

Architecture

Numéro de version

Affiché dans le titre de la fenêtre (config.VERSION, ex. GRP_2023-PRISME v3.4) — utile pour repérer d'un coup d'œil la version en cours sur un poste donné (ex. distinguer un collègue resté sur une version plus ancienne). Pourquoi deux sources de performance différentes

CRITERES_PERF.DAT (calage complet, exe 01+03) mesure la qualité de la simulation en connaissant tout l'épisode, en un seul passage pour tous les événements détectés. Le PDF Fiche_controle (rejeu, exe 04 + .bat) mesure la vraie performance de prévision opérationnelle à un instant donné, avec seulement les données disponibles jusque-là — un run par crue testée. Ce sont deux mesures complémentaires, pas interchangeables ; l'outil n'utilise la première que pour repérer les crues (onglet Crues), jamais comme résultat de campagne.

Le rejeu est positionné à la date de début de chaque crue détectée (modules/run_orchestrator.py — INSTPR = date_deb, mode Temps_diff, CONFIRM=NON pour un déroulement automatique). Cette démarche correspond exactement à la procédure « Mode temps différé : rejeu d'un événement historique » du Manuel d'utilisation GRP (INRAE, §3.5.5). Les indicateurs dQP/dTP/VE/KGE extraits du PDF (modules/fiche_controle_pdf.py) reprennent les définitions officielles du manuel (§2.4.10) : dQP = (QP−QO)/QO, dTP = tQP−tQO, VE = (moyP−moyO)/moyO, KGE selon Gupta et al. (2009).

⚠️ Aucun scénario de pluie future n'est fourni explicitement lors du rejeu (set_prevision() ne touche pas la section [SCENARIOS] de config_prevision.ini) : le comportement par défaut du mode temps différé s'applique, à savoir les pluies historiques réellement tombées après l'instant de prévision (équivalent au scénario « pluie future parfaitement connue » du manuel, §2.4.3). Les résultats de campagne représentent donc ce que le modèle peut atteindre au mieux, sans l'erreur liée à la méconnaissance des pluies futures — pas la performance qu'on obtiendrait en conditions opérationnelles réelles avec une vraie prévision de pluie (généralement moins bonne, d'autant plus que l'horizon dépasse le temps de réaction du bassin). À garder à l'esprit pour interpréter les scores de campagne.

Archivage des séries observée/simulée

<BDDTR>/Temps_Reel/Sorties/GRP*Obs.txt et GRP*Prev_*.txt (voir modules/grp_series.py) n'exposent que le dernier rejeu effectué — insuffisant pour retracer après coup la courbe simulée d'une combinaison/crue précise une fois la campagne terminée. run_orchestrator.py les archive donc immédiatement après chaque rejeu réussi (table series_archivees, liée à la combinaison et à la crue), et c'est cette copie archivée que le Dashboard relit — jamais le fichier « live » de Sorties/, qui pourrait correspondre à un tout autre run au moment de la consultation. Cet archivage est best-effort : un échec (fichier absent ou format inattendu) ne fait pas échouer la crue, qui garde son résultat dQP/dTP/VE/KGE (source primaire) — seule la courbe simulée manque alors dans le Dashboard, avec un message explicite.

Courbes Sim/Obs de « Détail par crue » et recalcul du dQP/dTP manquant

Dans Dashboard > Détail par crue, les deux courbes tracées sont toutes deux des valeurs numériques réelles issues de GRP, jamais extraites du PDF : « Q observé » vient de <code_site>-EVxxxx.DAT (modules/criteres_perf.py — parse_evenement_serie()), qui couvre toute la fenêtre de la crue détectée (avant et après le pic) ; « Sim » vient de la copie archivée du fichier GRP*Prev_*.txt du rejeu (table series_archivees, type sim — voir "Archivage des séries observée/simulée" ci-dessus). Le PDF Fiche_controle (modules/fiche_controle_pdf.py) sert uniquement à extraire les 4 indicateurs scalaires dQP/dTP/VE/KGE — un pipeline totalement séparé des courbes.

Constat (remonté par l'utilisateur) : sur certaines crues, GRP ne calcule pas de pic exploitable et le PDF ne renseigne donc pas dQP/dTP (case vide, sans que ce soit un échec — VE/KGE restent présents et cohérents puisqu'ils ne dépendent pas d'un instant de pic unique). Avant cette mise à jour, ce cas ne produisait aucun signal ailleurs que la case vide du tableau. modules/run_orchestrator.py tente désormais, immédiatement après un rejeu dont le PDF ne fournit pas dQP et/ou dTP, un recalcul à partir des séries réelles déjà archivées : _serie_observee_complete() relit le EVxxxx.DAT de la crue (la même source que la courbe « Q observé » du Dashboard, jamais la série archivée obs de series_archivees — celle-ci ne couvre que la fenêtre avant le rejeu, jamais le pic, et donne des valeurs aberrantes si on l'utilise à cette fin) ; _recalculer_dqp_dtp() applique ensuite les définitions officielles du manuel GRP (§2.4.10) : dQP = (QPsim−QPobs)/QPobs×100, dTP = tQPsim−tQPobs en nombre de pas de temps. Recalcul validé sur des crues où le PDF avait déjà fourni ces valeurs : dTP exact à chaque fois, dQP à moins de 0,1 point près dans la quasi-totalité des cas.

Que le recalcul réussisse ou non, une note explicite est désormais systématiquement générée dès qu'un indicateur manque encore après tentative ("dQP recalculé depuis les séries archivées", "dTP recalculé...", ou le motif d'échec si le recalcul lui-même n'a pas été possible — série trop courte, pic simulé introuvable, etc.) : plus jamais de case vide silencieuse. Cette note est stockée dans la colonne erreur de resultats_crues (colonne inutilisée jusqu'ici comme filtre de succès/échec — seul statut fait foi, la réutiliser ici ne risque donc pas de faire passer une crue réussie pour un échec ailleurs dans l'outil), affichée dans le journal de campagne au moment du rejeu, et exportée dans une nouvelle colonne « Note » de la feuille Excel Détail par crue.

⚠️ Ce recalcul ne s'applique qu'aux rejeux effectués après cette mise à jour. Les crues déjà en base avec dQP/dTP manquants avant cette date ne sont pas rétroactivement recalculées par ce correctif.

Journalisation et diagnostic des crashs

modules/journalisation.py configure la journalisation dès le démarrage (avant même la fenêtre principale) : tous les niveaux à partir d'INFO s'affichent à la fois sur la console (le cmd resté ouvert en fond) et dans un fichier logs/session_AAAAMMJJ_HHMMSS.log — un fichier par lancement, jamais écrasé. Chaque calage/rejeu GRP est journalisé juste avant son lancement (chemin, dossier, timeout) puis à sa fin (durée, code retour) : en cas d'arrêt sans message d'erreur exploitable, la dernière ligne du journal situe précisément l'exécutable qui était en cours. Les exceptions qui échapperaient aux try/except déjà en place (thread principal, thread de campagne, callbacks Tkinter) sont en plus capturées et journalisées avec leur trace complète.

Le mode QuickEdit de la console (Windows) est désactivé au démarrage : un simple clic ou une sélection de texte dans cette fenêtre gèlerait sinon tout le processus attaché — y compris les threads qui écrivent des logs — jusqu'à ce que la sélection soit relâchée, ce qui peut ressembler à une campagne plantée sans la moindre erreur. Conséquence : on ne peut plus sélectionner/copier du texte directement depuis cette console ; pour retrouver ce qui s'y est affiché, ouvrir plutôt le fichier logs/session_*.log correspondant dans un éditeur de texte (contenu identique, sans risque d'interrompre l'outil).

Rejeu à plusieurs instants avant le pic

Le rejeu habituel d'une campagne (une seule ligne resultats_crues par combinaison × crue) est positionné par GRP à la date de début de l'épisode — pas la date choisie par l'utilisateur, mais celle calculée par GRP lui-même à partir du champ NJ de LISTE_BASSINS.DAT (NJ=4 → fenêtre d'environ 2 jours avant le pic et 2 jours après). Cette date de référence convient à une logique de vigilance (le prévisionniste dispose de toute la fenêtre de montée), mais ne dit rien du comportement du modèle dans une logique de prévision, où l'instant de départ est bien plus proche du pic réel.

Les instants de rejeu supplémentaires (Paramétrage, liste éditable en heures avant le pic — ex. 24, 12, 6) permettent de rejouer chaque crue, en plus de la référence, à un instant positionné par rapport au pic réel (DateQmax de CRITERES_PERF.DAT) plutôt que par rapport à la fenêtre de détection. Le calage n'est jamais repris pour ces instants supplémentaires : seul le rejeu (GRP_PREVISION.BAT + extraction du PDF, ~20 s) est répété sur le dossier BDTR déjà calibré — pas besoin de multiplier le temps de calage (15-30 min) par le nombre d'instants testés.

Stockage purement additif : resultats_crues et series_archivees ont une colonne instant_label ('reference' = comportement historique, inchangé ; 'H-24'/'H-12'/'H-6'/... pour les instants supplémentaires). Toutes les requêtes qui pilotent la reprise sur échec, les badges de couverture (Paramétrage/Campagne) et le score composite (Dashboard) restent filtrées sur instant_label='reference' — les instants supplémentaires n'apparaissent JAMAIS dans ces calculs, pour ne changer aucun comportement existant. Ils sont journalisés séparément ("[instant H-24] ...") et exclus de la barre de progression de la campagne. Migration automatique et unique de l'ancien schéma (une seule ligne par combinaison × crue) vers le nouveau au premier lancement après cette mise à jour, sans perte des résultats déjà en base.

Visualisation dans Dashboard > Détail par crue : section "Comparaison des instants de rejeu (avant le pic)" sous le tableau des maximums — une grille (2 colonnes, autant de lignes que nécessaire) avec un panneau par instant testé (référence puis chaque décalage configuré), pour la crue et les combinaisons actuellement sélectionnées dans le graphique principal ci-dessus. Échelle Y commune à tous les panneaux (indispensable pour comparer directement l'amplitude d'un panneau à l'autre), seuils de vigilance repris sur chacun (respecte la case "Afficher les seuils de vigilance"). Volontairement plus simple que le graphique principal : pas de survol interactif ni de tableau récapitulatif par panneau, seule la comparaison visuelle est recherchée ici. Un panneau reste vide avec la mention "Pas encore de données" tant que la campagne n'a pas encore produit ce couple crue/instant.

Réutiliser pour un autre bassin

Rien n'est codé en dur : renseigner les 4 dossiers et le code station d'un autre bassin dans l'onglet Configuration suffit. Le seul réglage global figé par défaut est l'absence de module neige CemaNeige (avec_neige=False dans modules.liste_bassins.set_calage_params), validé pour Moussoulens — à passer à True dans le code pour un bassin de montagne qui en aurait besoin.

Les résultats de campagne sont automatiquement isolés par station : modules/results_store.py résout un fichier data/runs_<code_station>.sqlite3 distinct selon le code_station actuellement renseigné en Configuration (identifiant hydrologique stable, jamais le nom libre de la station — 2 orthographes différentes du même nom ne doivent jamais produire 2 bases pour une seule station, ni l'inverse). Basculer l'outil sur une autre station puis lancer une campagne ne peut donc plus mélanger ses résultats avec ceux d'une station déjà étudiée, même en cas d'horizon/seuil/méthode identiques entre les 2 — auparavant, un seul data/runs.sqlite3 partagé (sans aucune colonne station) aurait silencieusement réutilisé les lignes d'une autre station dans ce cas de figure. Migration automatique et unique au premier lancement après cette mise à jour : l'ancien fichier partagé, s'il existe encore, est renommé vers le fichier dédié de la station active à ce moment précis — à faire tourner une fois pendant que la station en cours d'étude est encore celle configurée, avant de basculer sur une nouvelle station.

Le changement de station n'est jamais silencieux : dès que le code station saisi diffère de celui déjà en config, cliquer sur « Identifier via PHyC » déclenche un message explicite — base vierge pour une station inédite, ou nombre de combinaisons déjà enregistrées si la station est déjà connue. Le titre de la fenêtre de l'outil affiche en plus, en permanence, le nombre de combinaisons actuellement en base ("... — N combinaison(s) en base") : un repère visible à tout moment, sans avoir à ouvrir un onglet, pour confirmer qu'on travaille bien sur la base attendue.

Même principe d'isolation par station pour la configuration de l'onglet Analyse crues affl. (modules/affluents.py, clé affluents_par_station de config/config.json) : chaque station garde sa propre liste d'affluents (nom, code station, surface, temps de propagation, fichier de débits, couleur) et son propre dossier d'import, restaurés automatiquement en rebasculant dessus.

Éviter de perdre ses résultats lors d'une réinstallation

data/ (les bases sqlite) et config/config.json sont volontairement exclus de Git (.gitignore — trop volumineux/spécifiques à chaque poste). Conséquence directe : toute nouvelle installation de l'outil (nouveau git clone, ou copie du dossier dans un autre emplacement — ex. GRP_2023-PRISME_v3 à côté d'un GRP_2023-PRISME_v2 existant) démarre nécessairement avec une base vierge, sans que l'ancienne installation (et ses résultats, restés dans l'ancien dossier) ne soit ni retrouvée ni signalée — incident réel constaté chez un utilisateur ayant mis à jour l'outil de cette façon plutôt qu'avec un git pull dans le dossier existant.

Deux garde-fous, indépendants et complémentaires :

  • Message au premier lancement (main.py::App._avertir_si_premier_lancement) : affiché UNE SEULE FOIS, exactement quand config/config.json vient d'être créé depuis le gabarit (donc jamais aux lancements suivants). Rappelle explicitement, au moment où ça compte, de copier data/ et config/config.json depuis une éventuelle ancienne installation avant de continuer — plutôt que de laisser l'utilisateur découvrir après coup qu'il travaille sur une base vide.
  • Dossier de stockage externe optionnel (bouton "Choisir un dossier externe…", onglet Configuration, bloc 3 — voir Utilisation) : un pointeur (%APPDATA%\GRP_2023-PRISME\data_emplacement.txt) indique un dossier de stockage des bases hors de l'installation de l'outil. Réglé une seule fois sur un poste, ce pointeur — contrairement à data/ — survit à n'importe quelle réinstallation future (nouveau dossier, nouveau clone) : modules.results_store.dossier_data_effectif() le relit systématiquement avant de résoudre le chemin d'une base, quel que soit le dossier d'installation courant. Solution durable, contrairement au message ci-dessus qui reste un simple rappel ponctuel.

Comportement par défaut strictement inchangé tant que ce dossier externe n'est pas configuré : dossier_data_effectif() retombe alors sur data/ dans le dossier d'installation, exactement comme avant l'ajout de ce mécanisme.
