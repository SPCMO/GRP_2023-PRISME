GRP_2023-PRISME — Campagnes de calage GRP

Documentation d'utilisation, d'architecture et de suivi des évolutions

Utilisation

À quoi sert cet outil

PRISME : Paramétrage, Recherche Itérative et Sélection du Meilleur Étalonnage.

GRP_2023-PRISME remplace la « boucle magique » (boucle_magique_relatif_absolu_HOR1_pdf.py) : un collègue avait écrit un script qui boucle sur des horizons de calage et rejoue des crues historiques pour trouver le meilleur horizon/seuil de calage du modèle hydrologique continu GRP (INRAE). Ce script contenait un bug critique (voir Correctifs) et n'était utilisable qu'en éditant le code Python à la main. Cet outil offre la même logique via une interface graphique, fiabilisée, et réutilisable pour n'importe quel bassin (pas seulement Moussoulens).

Premier lancement

Double-cliquer sur Test_pr_install.bat (vérifie/installe l'environnement Python), puis sur Lancer_GRP_2023-PRISME.bat.

Onglet Configuration

Dossiers de travail : 4 boutons Parcourir pour désigner 00_GRP_v2023, 00_Donnees_<station>, 00_BDDTR_<station> et 00_Resultats_<station> — leurs sous-arborescences sont fixes (imposées par les exécutables GRP), l'outil les déduit automatiquement une fois ces 4 chemins renseignés.

Identification station (PHyC) : saisir le code station (10 caractères : 1 lettre + 9 chiffres, ex. Y161202001) puis cliquer sur « Identifier via PHyC ». L'outil en déduit automatiquement le code site (8 caractères, les 2 derniers chiffres retirés — ex. Y1612020), qui est le code réellement utilisé dans LISTE_BASSINS.DAT et dans les noms de fichiers/dossiers générés par GRP. Le nom de la station, son code BNBV et ses 6 seuils de vigilance en débit (ZT jaune/Jaune/ZT orange/Orange/ZT rouge/Rouge) sont récupérés et affichés.

⚠️ Ces seuils PHyC sont différents des champs SeuilV1/SeuilV2/SeuilV3 internes à LISTE_BASSINS.DAT (utilisés par GRP pour sa propre analyse des résultats) — ne pas les confondre. Les deux sont affichés séparément dans le Dashboard.

Les identifiants PHyC (idcontact/mot de passe) sont demandés à la première identification et enregistrés dans config/config.json (jamais versionné dans le dépôt git).

Onglet Paramétrage

Choisir un pas de temps de calage, puis cocher les horizons à tester parmi ceux définis pour ce pas de temps (boutons « Tout sélectionner »/« Tout désélectionner »). Le bouton Paramètres… ouvre un écran dédié pour ajouter/modifier/supprimer/réorganiser aussi bien la liste des pas de temps que, pour chacun, la liste de ses horizons possibles — rien n'est codé en dur dans le programme.

Définir ensuite les seuils de calage (SeuilC1, en m³/s — débit minimal au-dessus duquel le calage est effectué, pour éviter de perturber le modèle en basses eaux) via une liste éditable, et cocher la ou les méthodes de correction à tester (Tangara / RNA — les deux cochées lancent les runs successivement pour chaque méthode, GRP n'acceptant qu'une seule méthode à la fois en mode BDTR).

Conseil : une campagne complète (tous les horizons × tous les seuils × toutes les crues) peut être très longue. Lancez d'abord une campagne sur quelques horizons/seuils espacés (grille grossière), consultez le Dashboard pour repérer la zone prometteuse, puis affinez avec une seconde campagne resserrée — les résultats des deux campagnes se cumulent automatiquement, pas besoin de tout refaire.

Onglet Crues

Les crues ne sont plus une liste figée dans le code : elles sont détectées automatiquement par GRP lui-même, lues depuis CRITERES_PERF.DAT (généré par le calage complet, exe 01 + exe 03) — chaque vignette affiche la date, le débit de pointe, les seuils de vigilance PHyC et les indicateurs dQP/dTP/VE/KGE de référence pour la configuration de calage actuellement en place. Une case « Inclure aussi les événements de pluie » élargit la liste aux événements pluviométriques (par défaut, seuls les événements de débit sont affichés). Cocher les crues à inclure dans la campagne.

Onglet Campagne

Bouton Lancer la campagne : boucle sur toutes les combinaisons horizon × seuil × méthode sélectionnées, et pour chacune, rejoue chaque crue cochée (mode opérationnel temps différé, comme la boucle magique d'origine mais avec le bug du .bat corrigé). La campagne tourne en arrière-plan, la fenêtre reste utilisable. La progression, un tableau des combinaisons avec leur statut, et un journal détaillé s'affichent en temps réel.

Si des combinaisons ou des crues ont échoué (erreur explicite dans le journal), le bouton Relancer les échecs ne refait que le nécessaire : si le calage d'une combinaison a déjà réussi, il n'est pas relancé — seules les crues manquantes ou en échec le sont.

Onglet Dashboard

Vue synthèse : heatmap horizon × seuil (score composite combinant dQP/dTP/VE/KGE, 0 = meilleur), classement des meilleures combinaisons, dispersion de |dQP| par horizon. Bouton d'export Excel (classeur Détail + Synthèse) à la demande.

Détail par crue : courbe du débit observé (large fenêtre, depuis CRITERES_PERF.DAT) avec la courbe du débit simulé superposée (archivée au moment du rejeu — voir Architecture) et les seuils de vigilance PHyC, pour la crue et la combinaison choisies. Si aucune courbe simulée n'apparaît, c'est que cette combinaison/crue précise n'a pas encore été rejouée (ou que le fichier GRP correspondant était absent au moment du run — message explicite affiché sous le graphique dans ce cas).

Sensibilité au seuil : évolution du score composite et du KGE moyen en fonction du seuil de calage, à horizon et méthode fixés — utile pour la phase d'affinage évoquée ci-dessus.

Ce qui est différent de GMAO (pas de front/back séparés)

GMAO est une application web : deux programmes séparés qui se parlent par le réseau. GRP_2023-PRISME est une application desktop : un seul programme, tout tourne dans le même processus. Ni serveur à démarrer, ni navigateur, ni port à ouvrir.

GMAO — application web

  • Front : navigateur (pages HTML + Leaflet.js)
  • Back : serveur Flask (run.py), à lancer séparément
  • Front ↔ Back : requêtes HTTP sur localhost:5000
  • Utilisable depuis plusieurs postes via le réseau

GRP_2023-PRISME — application desktop

  • Un seul programme : main.py (fenêtre Tkinter)
  • Pas de serveur, pas de navigateur, pas de port réseau
  • L'interface et la logique s'appellent directement en mémoire
  • Un seul poste à la fois (comme OPALE v2)

Architecture

Choix structurants

  • Interface Tkinter desktop (comme OPALE v2), pas d'application web.
  • Source des résultats de campagne : exclusivement le rejeu opérationnel (exe 04 + GRP_PREVISION.BAT, comme la boucle magique d'origine — bug corrigé). CRITERES_PERF.DAT (exe 01 + exe 03) sert uniquement, en lecture seule, à la détection automatique des crues (onglet Crues) — ce n'est pas la même mesure de performance (calage complet vs prévision opérationnelle réelle à un instant donné).
  • Outil générique, pas figé sur Moussoulens : voir modules/station_codes.py et la section « Réutiliser pour un autre bassin » ci-dessous.

Pourquoi deux sources de performance différentes

CRITERES_PERF.DAT (calage complet, exe 01+03) mesure la qualité de la simulation en connaissant tout l'épisode, en un seul passage pour tous les événements détectés. Le PDF Fiche_controle (rejeu, exe 04 + .bat) mesure la vraie performance de prévision opérationnelle à un instant donné, avec seulement les données disponibles jusque-là — un run par crue testée. Ce sont deux mesures complémentaires, pas interchangeables ; l'outil n'utilise la première que pour repérer les crues (onglet Crues), jamais comme résultat de campagne.

Archivage des séries observée/simulée

<BDDTR>/Temps_Reel/Sorties/GRP*Obs.txt et GRP*Prev_*.txt (voir modules/grp_series.py) n'exposent que le dernier rejeu effectué — insuffisant pour retracer après coup la courbe simulée d'une combinaison/crue précise une fois la campagne terminée. run_orchestrator.py les archive donc immédiatement après chaque rejeu réussi (table series_archivees, liée à la combinaison et à la crue), et c'est cette copie archivée que le Dashboard relit — jamais le fichier « live » de Sorties/, qui pourrait correspondre à un tout autre run au moment de la consultation. Cet archivage est best-effort : un échec (fichier absent ou format inattendu) ne fait pas échouer la crue, qui garde son résultat dQP/dTP/VE/KGE (source primaire) — seule la courbe simulée manque alors dans le Dashboard, avec un message explicite.

Réutiliser pour un autre bassin

Rien n'est codé en dur : renseigner les 4 dossiers et le code station d'un autre bassin dans l'onglet Configuration suffit. Le seul réglage global figé par défaut est l'absence de module neige CemaNeige (avec_neige=False dans modules.liste_bassins.set_calage_params), validé pour Moussoulens — à passer à True dans le code pour un bassin de montagne qui en aurait besoin.

Paramétrage

Proxy sortant du réseau RIE

Comme GMAO et OPALE v2, le proxy réseau SPCMO/RIE est en dur dans config.py (PROXY_RIE) car pip/git ne le détectent pas automatiquement contrairement à un navigateur. Une variable d'environnement HTTPS_PROXY, si définie, reste prioritaire.

Installer l'outil sur un nouveau poste

  1. Copier le dossier GRP_2023-PRISME (ou cloner le dépôt git).
  2. Double-cliquer Test_pr_install.bat — détecte/mémorise le Python à utiliser, vérifie et installe les dépendances manquantes (proxy RIE automatique si besoin).
  3. Double-cliquer Lancer_GRP_2023-PRISME.bat.
  4. Onglet Configuration : renseigner les 4 dossiers de travail et identifier la station via PHyC.

Dépôt GitHub

Code hébergé sur github.com/SPCMO/GRP_2023-PRISME. Authentification par token dans l'URL du remote git, comme les dépôts GMAO et OPALE v2 (voir la remarque de sécurité ci-dessous).

⚠️ Ce pattern d'authentification stocke le token en clair dans .git/config, lisible par quiconque a accès au dossier local. Choix assumé pour rester cohérent avec l'existant (GMAO, OPALE v2) — l'alternative plus sûre (Git Credential Manager, token jamais stocké en clair) a été proposée et écartée en connaissance de cause.

Correctifs & nouvelles fonctionnalités

20 août 2026

Correctif critique Le script d'origine (boucle_magique_relatif_absolu_HOR1_pdf.py) pointait bat_file vers le dossier Temps_Reel au lieu du fichier GRP_PREVISION.BAT lui-même. Sur Windows, exécuter via shell=True une commande qui est un chemin de dossier valide revient à un cd implicite : la commande « réussissait » (code retour 0) sans jamais lancer réellement le rejeu — le script relisait alors un PDF périmé. Tous les résultats produits par le script d'origine sont donc potentiellement invalides. Corrigé dans modules/grp_runner.py : chemin de fichier exigé explicitement, et garde-fou supplémentaire vérifiant qu'un nouveau PDF apparaît bien après le lancement.

20 août 2026

Correctif SELECTION_EVT.DAT s'est révélé encodé en UTF-8 alors que LISTE_BASSINS.DAT et config_prevision.ini sont en cp1252 — le pipeline GRP mélange les encodages selon l'étape qui génère le fichier. modules/criteres_perf.py détecte désormais l'encodage automatiquement (UTF-8 en priorité, repli cp1252) plutôt que de supposer un encodage fixe.

20 août 2026

Correctif Le mécanisme de reprise sur échec ignorait à tort les crues en échec d'une combinaison dont le calage avait par ailleurs réussi. modules/run_orchestrator.py distingue maintenant explicitement le statut du calage (par combinaison) et celui de chaque crue rejouée, avec reprise à la bonne granularité.

20 août 2026

Nouveauté Mise en ligne initiale : interface Tkinter complète (Configuration, Paramétrage, Crues, Campagne, Dashboard), détection automatique des crues via CRITERES_PERF.DAT, orchestrateur de campagne fiabilisé avec reprise sur échec fine, dashboard (heatmap horizon×seuil, score composite, sensibilité au seuil), export Excel, réutilisable pour n'importe quel bassin.

20 août 2026

Nouveauté Bouton Annuler sur une campagne en cours (onglet Campagne) — vérifié entre chaque étape, jamais en cours d'exécution d'un exe GRP ; les combinaisons/crues non traitées restent reprenables normalement.

20 août 2026

Correctif Trouvé lors d'une relecture à froid du code : le nettoyage final du dossier BDTR (confirmé sans risque, déjà implémenté dans modules/grp_runner.py) n'était jamais appelé par l'orchestrateur — corrigé, appelé désormais à toute sortie de la campagne (fin normale ou annulation).

20 août 2026

Nouveauté Courbe Q simulé superposée à l'observée dans le Dashboard > Détail par crue. La série est archivée en base à chaque rejeu réussi (table series_archivees) plutôt que relue depuis Sorties/, qui n'expose que le dernier run — voir Architecture > Archivage des séries observée/simulée.
